# 05 · 踩坑记录

这里记录的每一个坑都是**实际发生过的**，不是假设。每条都写清
「现象 → 原因 → 修法」，便于以后快速定位。

---

## A. 部署相关

### A1. `default_server` 抢走整个端口的请求，搞挂别人的站点

**现象**：配置应用后，服务器上**另一个在用域名**的 HTTP 访问变成 503。
`https` 正常，`http` 503。而随便编一个不存在的域名访问，也返回 503。

**原因**：Nginx 官方文档《How nginx processes a request》：

> 若 Host 不匹配任何 server name，nginx 会把请求交给**该端口的默认 server**。
> **默认 server 是监听端口的属性，而不是 server name 的属性。**

我为了让自己网站的 ACME 校验不被现有通配块接走，给我们的块加了
`listen 80 default_server`。结果**所有未匹配的 Host 都落到我们块上**，
命中 `return 503`，把别人在用的站点搞挂了。

**修法**：不要声明 `default_server`。改用 `--standalone` 方式申请证书
（申请瞬间独占 80 端口，需短暂停容器）。

**教训**：`default_server` 的语义是「接管这个端口上所有未定义的域名」。
**在共用端口上声明它，是越权。** 正确做法是让自己的方案适应环境，
而不是改环境来迁就自己的方案。

### A2. `rsync --delete` 在产物为空时清空站点目录

**现象**：脚本报告「发布成功」，但线上实际是 nginx 默认 404，
所有路径（含 `robots.txt`、`sitemap`）全部 404。站点目录被清空。

**原因**：发布用的是 `rsync -a --delete dist/ "$SITE_ROOT/"`。
当构建失败或产物不完整时，`dist/` 为空，`--delete` 就把服务器上的
站点目录整个删掉了。原脚本只检查了「`index.html` 是否存在」，
拦不住「产物存在但内容不完整」。

**修法**：两道防御。

1. **发布前产物门禁**，任一不满足即中止，不做任何同步：
   - `dist/index.html` 存在且 ≥ 5000 字节
   - `dist/_astro` 文件数 ≥ 50
2. **同步前自动备份**当前线上内容为 `<SITE_ROOT>.prev`

**教训**：`--delete` 是「让服务器与本地完全一致」的语义，
**在输入不可信时它就是删库工具**。破坏性操作前必须验证输入有效，
并留退路。

### A3. 发布"成功"但实际是 404 —— 静默失败

**现象**：脚本打印「发布成功」，但线上 404。直到人工发现才知道。

**原因**：脚本只检查了命令退出码，**没有验证最终结果**。

**修法**：`publish.sh` 增加**发布后自检 + 自动回滚**：

| 检查 | 失败后果 |
| --- | --- |
| 站点目录有 `index.html` 且 ≥ 5000 字节 | 回滚 |
| 页面引用的 `_astro` 资源真实存在 | 回滚 |
| 线上返回 200 | 只提示（可能是网络问题） |

**教训**：**"命令没报错" ≠ "事情做成了"**。关键流程要有结果验证。

### A4. `date -d` 是 GNU 专有，BSD/macOS 不支持

**现象**：证书有效期比较逻辑失效，所有证书被算成同一时间。

**原因**：`date -d` 是 GNU coreutils 的扩展，BSD `date` 不支持。
更糟的是**解析失败会静默返回空值**，导致比较逻辑形同虚设。

**修法**：改用 `openssl x509 -checkend`，它不依赖日期解析，
用「剩余有效期是否超过 N 秒」来判断。

**教训**：跨平台脚本不要用平台专有命令；**解析失败必须有处理**，
不能静默变成默认值。

### A5. 续行符写成 `\\` 导致命令残缺

**现象**：`certbot` 报 `unrecognized arguments: \`，
且报 `-d: command not found`。

**原因**：脚本里行尾续行符写成了**两个反斜杠**，导致参数里混入字面反斜杠，
后续行被 shell 当作独立命令执行。**certbot 从头到尾没有真正运行。**

**修法**：改为单个 `\`。并在提交前用 `bash -n` + 实际执行验证。

**教训**：写在文件里的脚本，**转义层数极易出错**（尤其是通过程序生成时）。
写完要检查实际字节，不能只看渲染结果。

### A6. `if` 条件吸收 `set -e`，失败被当成成功

**现象**：certbot 输出 `Successfully received certificate`，
但脚本报「证书申请失败」，且没有安装证书。

**原因**：写法是 `if certbot ... | sed ...; then`。
certbot 是**管道第一段**，需要 `PIPESTATUS[0]` 才能准确取到它的退出码；
而放进 `if` 条件后，**条件语句会吸收 `set -e`**，失败被当作正常分支。

**修法**：先执行、再紧接读取 `PIPESTATUS[0]`：

```bash
set +e
certbot ... 2>&1 | sed 's/^/  /'
RC=${PIPESTATUS[0]}      # 必须紧接管道，中间不能插入其它命令
set -e
```

**注意**：不能用 `$?` —— 赋值动作本身会把 `PIPESTATUS` 冲掉。

**教训**：管道 + 退出码 + `set -e` 三者组合坑很多，**必须实测**。

### A7. 证书钩子与"停容器"逻辑互相打架

**现象**：证书**签发成功**（输出显示有效期已更新），
但因为钩子报错，certbot 整体返回非 0，脚本误判为失败并提前退出，
**证书没被安装**。

**原因**：续期时 pre 钩子刚把容器停掉（standalone 需独占 80 端口），
而 deploy 钩子直接执行 `docker exec ... nginx -s reload` ——
容器未运行必然失败，钩子返回非 0 使 certbot 整体返回非 0。

**修法**：钩子内所有命令以 `|| true` 结尾并显式 `exit 0`；
重建容器时优先使用含挂载的 `docker-compose.effective.yml`，
避免续期后容器丢失挂载配置。

**教训**：**钩子失败 ≠ 主任务失败**，两者退出码要解耦。
另外，**我自己写的两个机制互相冲突了** —— 各部分单独看都对，
组合起来才暴露问题。

### A8. NodeSource 的 apt 源在国内不可靠，且失败是静默的

**现象**：`curl -fsSL https://deb.nodesource.com/setup_22.x | bash -` 后，
`apt update` 报 `Some index files failed to download`，
最后**装成了 Ubuntu 自带的 Node 18**，而 18 不带 `corepack`，
构建阶段才失败（问题被推迟暴露）。

**原因**：apt 源依赖仓库元数据，国内网络下不稳定；
而 NodeSource 脚本在 `apt update` 失败后没有让整体失败。

**修法**：`bootstrap-node.sh` 改为下载 **Node 官方预编译包**
（单次 HTTPS），并用官方 `SHASUMS256.txt` 校验 SHA256，
解压到 `/usr/local`（该目录在 PATH 中优先于 `/usr/bin`）。

**教训**：**优先选择不依赖包管理器的方案**；
另外要警惕「失败但退出码为 0」的脚本。

### A9. `.nvmrc` 会让云构建平台去下载不存在的版本

**现象**：EdgeOne 构建在「安装依赖」阶段失败：
`Switching error: Failed to switch to Node.js 24.12.0`

**原因**：仓库里的 `.nvmrc` 指定了 24.12.0，
平台会据此去下载该版本，但它不在平台预装列表内
（预装：14.21.3 / 16.20.2 / 18.20.4 / 20.18.0 / 22.11.0 / 22.17.1 / 24.5.0）。

**修法**：移除 `.nvmrc`，改用平台预装版本；
项目 `engines` 只要求 `>=22.12.0`，预装的 22.17.1 或 24.5.0 都满足。

---

### A10. `pnpm-workspace.yaml` 缺少 `packages` 字段

**现象**：pnpm 9（云平台支持的版本）报 `packages field missing or empty`。

**原因**：pnpm 11 会自动往这个文件写 `minimumReleaseAgeExclude`
（某个包因「新版本冷却期」被拦时需要豁免），但它生成的版本
**缺少必需的 `packages` 字段**，pnpm 9 会因此报错。

**修法**：单包项目也保留该文件，但补上 `packages: ['.']`，
让两个版本都能正常工作。

---

### A11. `default_server` 是 `listen` 的参数，不是独立指令

**现象**：nginx 报 `unknown directive "default_server"`。

**原因**：写成了独立指令：

```nginx
listen 80;
default_server;          # ❌ 不是指令
```

正确写法是作为 `listen` 的参数：

```nginx
listen 80 default_server;  # ✅
```

**修法**：改正。并在 `validate_nginx.py` 里加了专门的检查 ——
把这类「参数被误写成指令」的错误在推送前拦下。

---

### A12. `http2` 指令的两种写法互不兼容

**现象**：不确定该用哪种写法。

**原因**：
- `listen 443 ssl http2;` —— 在 nginx ≥ 1.25.1 上**已废弃**（会打警告）
- `http2 on;` —— 在 nginx < 1.25.1 上是**未知指令，直接启动失败**

**修法**：先确认版本（`docker exec ... nginx -v` → 实测为 1.31.1），
再按版本选用 `http2 on;`。

**教训**：**写平台相关配置前先确认版本**，不要按记忆写、等报错再改。

## B. 前端相关

### B1. 入场动效导致正文在慢设备上不可见

**现象**：Lighthouse 无障碍从 100 掉到 **27 处对比度不合格**。

**原因**：入场动效用了 `opacity: 0 → 1`。在模拟限速/慢设备下，
动画未跑完时正文处于半透明状态，对比度不足。

**修法**：改为**只动 transform，不动 opacity**；
并加 2.6 秒兜底（不依赖 IntersectionObserver 的情况）。

---

### B2. `hidden` 属性被 `display: flex/grid` 覆盖，透明层拦截全页点击

**现象**：灯箱和移动端抽屉关闭后，**整个页面的点击都失效**。

**原因**：`hidden` 属性的 `display: none` 会被组件里更高优先级的
`display: flex/grid` 覆盖，元素实际仍然存在，形成一个**不可见但占满屏幕的层**，
拦截了所有点击。

**修法**：改用 `.is-open` 类 + `opacity` / `visibility` / `pointer-events`，
并给 `visibility` 加延迟过渡。

**教训**：**不要用 `hidden` 属性配合会设置 `display` 的类**。

---

### B3. 灯箱复用缩略图的 srcset，放大后只有 432px

**现象**：点击放大后图片模糊，`naturalWidth` 只有 432。

**原因**：灯箱直接复用了缩略图的 `srcset`，那个尺寸是为网格设计的。

**修法**：用 `getImage()` 单独生成大尺寸变体（现在 `naturalWidth` 1150）。

---

### B4. 首屏用两个 `<img>` + CSS 显隐做艺术方向，导致多下载 210KB

**现象**：手机端首屏图片总下载 565KB（两张都下了）。

**原因**：桌面用横构图、手机用竖构图，写成了两个 `<img>` 互相 `display: none`。
**浏览器两张都会下载。**

**修法**：改用原生 `<picture><source media="...">`，
浏览器只下载命中的那一版。**省下 210KB。**

---

### B5. 图片质量参数：`effort` 几乎不影响质量，只影响耗时

**背景**：服务器首次构建要生成 335 个图片变体（108 个 avif），很慢。

**实测**（同一张 1600px 图）：

| 参数 | 耗时 | 体积 | 与 effort:6 的像素差 |
| --- | --- | --- | --- |
| `effort: 6` | 2285ms | 342KB | — |
| `effort: 4` | 1214ms | 340KB | 平均 3.9/255（不可见） |
| `effort: 2` | 139ms | 343KB | 平均 4.4/255 |

**结论**：真正控制质量/体积的是 `quality`，`effort` 只决定编码器搜多深。
**降到 4 省一半时间，质量几乎不变。**

---

### B6. 固定尺寸的圆形徽标装不下多个汉字

**现象**：图片上的「果园全貌」标签折成两行，溢出圆圈。

**原因**：`.kicker > span` 是固定的 32×32 圆形，本意装 `01`/`02` 这类序号。
但 4 个汉字约 50px 宽，装不下就折行。
实测 **桌面端同样存在**（不只手机）。

**修法**：改为 `min-width/min-height` + 药丸圆角（`border-radius: 999px`）：

```
「果园全貌」→ 68×32 单行药丸
「01」序号  → 32×32 仍为正圆
```

**教训**：为某类内容（数字）设计的固定尺寸容器，
换成另一类内容（文字）时要重新审视。

---


### B7. 导航标签与区块标题用词不一致

**现象**：导航写「为什么套袋」，点进去后该区块的标题却写「为什么值得」。
两处指同一个区块，用词却不同。

**原因**：导航标签定义在 `src/lib/links.ts`，区块标题写在各自的组件里，
**两处靠人工维护，容易漂移**。这次就是改了导航、忘了改区块。

**修法**：统一为「为什么套袋」（导航的描述更准确）；
并新增 `tools/check-labels.py` 自动校验两者一致，
已接入 `pnpm build` —— 不一致会直接构建失败，不会再悄悄漂移。

**教训**：**同一个信息存在两处就会不一致。**
要么收敛成单一来源，要么加自动检查。这里选择了后者，
因为导航词和标题在视觉语境上本就可以不同，不宜强行合并。

## C. 流程与协作相关

### C1. 先查平台文档，再动手

这次在 EdgeOne 上先部署、遇到 401、才去查文档。
**如果一开始就查，能省下好几轮折腾。**

### C2. 无法实测的逻辑，要求对方提供输出

部署脚本运行在别人的服务器上，我无法直连。
早期几次都是"我推脚本 → 对方报错 → 我再改"，
效率低且容易反复。

**改进**：把诊断也写进脚本（如 `recover.sh`），
让它自己打印判断依据，输出即排查材料。

### C3. 能本地验证的一定要验证

这一轮 12 个坑里，**有 5 个（A4/A5/A6/A7/A11）的根因是
"我写脚本时靠推演，没实测组合行为"**。

现在尽量把关键逻辑抽出来本地实测：

- 门禁逻辑 → 四种失败场景逐一验证
- 证书比较 → 三种场景（更新/更旧/不存在）
- Nginx 配置 → 静态校验器 + 括号配对
- 回滚路径 → 用真实文件操作跑一遍

**"我检查过了"必须是实测，不能是"我觉得没问题"。**
